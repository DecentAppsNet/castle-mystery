# ADR 023: Second-Pass Timeline Adjustments

## Status

Approved

## Context

The first-pass activity scheduling loop encapsulates each activity's scheduling behavior. Additional passes introduce special cases and ordering dependencies between adjustments. Accumulating these dependencies risks a three-or-more-pass system that is harder to understand and maintain.

## Proposed Decision

### 1. Require information unavailable in the first pass

Use a second-pass timeline adjustment only when information generated by the first pass is needed to make that adjustment correctly. Demonstrate the dependency using valid authored content and actual scheduling behavior, including activity ordering and conflict validation; do not assume that a hypothetical scenario can load successfully.

### 2. Consider alternatives before adding another pass

When second-pass handling appears necessary, first consider resolving the behavior within the first-pass scheduler, supplying current draw-call context to the effect handler, or changing requirements to avoid the adjustment. A second pass may still be chosen, but only after evaluating these alternatives and their correctness, simplicity, runtime cost, and ordering dependencies.

For behavior that depends on current rendered state rather than a scheduling decision, consider using existing `EffectDrawCall` context members or adding focused members to the relevant draw context. This lets the effect handler respond to finalized current-frame state without capturing incomplete first-pass state or adding a timeline adjustment pass. Evaluate the cost and scope of producing that context; draw-time handling does not replace scheduling or authored-content validation.

### 3. Document dependencies in second pass handling

If a second-pass timeline adjustment is determined to be the best solution, any prerequisites must be documented in source comments. This is so we can update second-pass handling without introducing bugs caused by sequence of calls.

## Rationale

Prefer encapsulated scheduling and fewer special cases. Correctness can justify an additional pass, but convenience alone does not establish that need. Small requirement changes may be preferable when they substantially simplify implementation without meaningful loss to authoring or gameplay.
