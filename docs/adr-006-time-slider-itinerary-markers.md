# ADR 006: TimeSlider Itinerary Markers

## Status

Proposed

## Context

The TimeSlider currently renders only:

- the thumb position
- time labels
- play/pause controls
- the current formatted time text

It does not yet visualize any itinerary-derived events.

The next intended design is for the TimeSlider to show timeline annotations for the active character's itinerary:

- room entry events as small black vertical ticks
- speech activity as yellow timeline spans clustered across short gaps of silence
- character encounter events as compact stick-figure markers

These annotations would be shown beneath the horizontal slider line with a height similar to the height of labels, which are shown above the slider line.

There are two important constraints:

- the slider should remain a mostly presentational React component rather than becoming a second gameplay engine
- itinerary data is immutable after level load, but the active character can change during play, so React props must update when the active character changes

There is already one example of game-state changes being forwarded from the canvas/game loop back into React state:

- `LevelView` passes `onMinutesChanged` into `updateAndDraw()`
- `HomeScreen` stores that value in React state
- `TimeSlider` receives the updated prop

The same pattern is the most natural fit for active-character-driven itinerary updates.

## Decision

We will extend the TimeSlider to render itinerary markers by passing the active character's itinerary from React state and deriving a slider-specific marker view model from it.

### 1. `TimeSlider` accepts an `itinerary` prop

`TimeSlider` should receive the active character's immutable itinerary as a prop from `HomeScreen`.

It should not read directly from `GameState` or from gameplay utilities.

This keeps the component in the React tree and avoids coupling slider rendering to mutable canvas state.

### 2. `HomeScreen` tracks the active character in React state

A new callback path should mirror the existing minutes flow:

1. `gameUtil.updateAndDraw()` detects when the active character changes
2. `LevelView` forwards that callback to React
3. `HomeScreen` stores the active character id or index in React state
4. `HomeScreen` derives the active character's itinerary from `gameState.initialCharacters`
5. `HomeScreen` passes that itinerary into `TimeSlider`

The itinerary should be derived from `initialCharacters`, not from the mutable current `characters` array, because itineraries do not change after level load.

### 3. `TimeSlider` uses a dedicated marker-derivation utility

`TimeSlider` should not directly implement itinerary analysis logic.

Instead, a focused utility should translate an itinerary into a marker view model containing:

- room-entry tick times
- clustered speech ranges
- encounter marker times

This keeps `TimeSlider` mostly concerned with layout and rendering while keeping event analysis testable in isolation.

### 4. Room-entry events render as black vertical ticks

Each `RoomEntryEvent` should render as a small black vertical line under the slider inset.

Positioning should reuse the same width measurements and time-to-position math already used for labels and thumb alignment so the markers remain consistent across resize and responsive layout changes.

### 5. Speech markers render as clustered spans

Speech markers should be built from `SpeechEvent` ranges:

- each speech event contributes a raw range from `startTime` to `startTime + duration`
- raw ranges should be sorted by time
- adjacent ranges should be merged when the silence gap between them is less than or equal to a named constant such as `SPEECH_CLUSTER_GAP_MSECS`

Each merged range should render as a rectangle with:

- thin black outline
- fill color from the same constant used by speech bubbles

This preserves visual continuity between timeline speech markers and in-scene speech bubbles.

### 6. `CharacterEncounterEvent` becomes a first-class itinerary event type

Character encounters should not be computed ad hoc in `TimeSlider`.

Instead, a new `CharacterEncounterEvent` should be added to the itinerary event model.

A minimal event shape should include:

- `startTime`
- `duration: 0`
- `encounteredCharacterId` or equivalent encounter payload

If multiple characters are encountered at the same time - a single event should be used for all characters encountered.

This keeps encounter semantics in the itinerary/domain layer, where they can be tested and reused.

### 7. Encounter events are generated during itinerary postprocessing

Encounter events require cross-character temporal analysis.

They should be generated by a focused utility during level-load or itinerary-postprocessing, not during rendering.

An encounter occurs when, from the perspective of a specific itinerary character, another character becomes newly present in the same room.

That includes both:

1. the itinerary character entering a room that is already occupied by another character
2. another character entering the room the itinerary character is already in

Because this requires comparing occupancy transitions across multiple itineraries, it should be treated as a separate domain-level step rather than mixed into slider rendering logic.

### 8. Encounter markers render as compact stick-figure icons

Each `CharacterEncounterEvent` should render as a small stick-figure marker beneath the slider.

It should be visually lighter than speech spans so the slider remains readable when multiple kinds of annotation appear together.

## Rationale

This design keeps responsibilities separated cleanly:

- React owns which itinerary is currently shown
- domain utilities own event derivation and clustering rules
- `TimeSlider` owns layout and drawing of markers

Using the existing callback pattern from `LevelView` to `HomeScreen` avoids introducing a second state synchronization mechanism just for the active character.

Making encounters first-class itinerary events avoids burying cross-character reasoning in UI code and keeps the harder logic in a place where it can be tested with fixtures.

Speech clustering belongs in a marker utility rather than in JSX because it is a pure timeline transformation with clear input/output behavior and edge cases.

## Consequences

### Positive

- `TimeSlider` remains mostly presentational
- active-character changes update slider props through an existing architectural pattern
- room-entry and speech markers can be derived with small, testable pure utilities
- encounter semantics become reusable domain data rather than UI-only calculations
- marker layout remains aligned with existing slider measurement logic

### Negative

- a new callback is needed from the gameplay loop back into React for active-character changes
- a new itinerary event type expands the domain model and related duplication/type handling
- encounter generation requires non-trivial cross-character temporal analysis
- the slider will become visually denser and will need careful CSS/layout tuning

## Implementation Notes

Implementation should proceed in phases:

1. Add React-side tracking for the active character using the `LevelView` -> `updateAndDraw()` callback pattern.
2. Pass the active character's itinerary from `HomeScreen` into `TimeSlider`.
3. Add a marker-derivation utility for room-entry ticks and clustered speech spans.
4. Render the room-entry and speech markers in `TimeSlider` using existing slider width measurements.
5. Introduce `CharacterEncounterEvent` into itinerary event types and duplication helpers.
6. Add a level-load or itinerary-postprocessing step that emits encounter events.
7. Render encounter markers in `TimeSlider`.
8. Add targeted tests for speech clustering and encounter generation.

## Not Chosen

### Computing all marker logic directly in `TimeSlider`

Not chosen.

Reason:

- it would make the component responsible for domain analysis
- clustering and encounter derivation are easier to test outside JSX
- the component would become harder to maintain as new marker types are added

### Reading the active itinerary directly from mutable `gameState.characters`

Not chosen.

Reason:

- the mutable character array is rebuilt over time
- itineraries are immutable after level load
- `initialCharacters` is the more stable source of authored itinerary data

### Computing encounter markers only in the UI layer

Not chosen.

Reason:

- encounters depend on cross-character temporal reasoning
- UI code should not become responsible for reconstructing occupancy semantics
- first-class itinerary events provide a cleaner reusable representation

### Delaying active-character prop updates until user input handlers run in React

Not chosen.

Reason:

- active-character changes currently happen inside gameplay/canvas logic
- React already receives derived values from the game loop through callbacks
- reusing that pattern minimizes architectural drift
